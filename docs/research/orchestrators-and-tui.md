# Orchestrators and TUI building blocks: reuse or build?

Research for issue #6 (map #1, "Agent factory v1"). Gathered 2026-10-14 from primary sources: each project's own repo, README, source, release list and npm metadata, plus Microsoft and Anthropic docs. Repo metadata (licence, last push, latest release) comes from the GitHub API on that date. Anything not confirmed in a primary source is marked **(unverified)**.

## Answer in brief

- **Build, don't adopt.** No existing orchestrator fits the factory's shape: Node/TS, native Windows, task trees, autonomy levels, attention queue, metrics. Each one is either Mac/Linux-only (tmux), a desktop or web GUI, sunsetting, or a different paradigm. Two are worth **mining for patterns and code ideas**: **ccmanager** (MIT, Ink + headless xterm, the closest stack match) and **vibe-kanban** (Apache-2.0, drives Claude Code headlessly over its stream-JSON control protocol).
- **TUI framework candidates:** **Ink 8** (mature, React, Node >= 22, used by Claude Code and Gemini CLI) is the safe default. **OpenTUI 0.6** (Zig core, React/Solid bindings, built-in embedded-terminal widget, mouse, scroll boxes) is the more capable but riskier option: it is pre-1.0, Bun-first, and on Node it needs Node >= 26.4 with `--experimental-ffi`. **blessed / neo-blessed are dead** (last publishes 2015 / 2018). Rule them out.
- **Embedding interactive Claude Code sessions on Windows is feasible.** `node-pty` 1.1.0 (ConPTY, prebuilt Windows binaries, optional bundled `conpty.dll`) plus `@xterm/headless` 6.0.0 is a proven combination, and ccmanager ships exactly this. The known breakage is concentrated in Windows 10's inbox ConPTY: no reflow on resize below build 21376, output re-encoded by ConPTY, mouse tracking broken on Windows 10, and cursor-position requests that must be answered. The operator's machine is Windows 10 build 19045, so the factory should default to node-pty's bundled `conpty.dll` and test that path early.

### What to reuse vs learn from

**ccmanager: learn from, closest analogue.** It is the same stack the factory wants (TS, Ink, headless xterm) and it is MIT, so code can be borrowed with attribution.
- *Session model.* Each session is a PTY whose output feeds a per-session `@xterm/headless` terminal. When the operator attaches, ccmanager clears the screen, writes a serialized snapshot (`@xterm/addon-serialize`), then passes raw PTY output straight through to stdout. Ink renders only the menu ([Session.tsx](https://github.com/kbwo/ccmanager/blob/main/src/components/Session.tsx)). This "full-screen attach with snapshot restore" is the cheapest, most faithful way to embed a live Claude Code conversation. It sidesteps re-rendering a terminal grid inside an Ink box.
- *Terminal hygiene on attach.* Before handing the screen to the child it disables kitty keyboard protocol, modifyOtherKeys, focus reporting and bracketed paste, and re-enables auto-wrap. It also batches PTY chunks and honours DEC 2026 synchronized output (8 ms flush, 100 ms sync timeout).
- *State detection* (busy/waiting/idle) is done by screen-scraping per agent. For Claude Code specifically, ccmanager appends `--teammate-mode in-process` to avoid clashes with agent teams. The factory can do better with Claude Code hooks (Notification/Stop) for its attention queue. Screen-scraping should be the fallback.
- *Also worth copying:* restoring sessions after a crash (`sessions.json`), `.worktreeinclude` for gitignored files, and status-change hooks.
- *Caveat:* ccmanager moved from `node-pty`-style PTYs to Bun's built-in `Bun.Terminal` (ConPTY on Windows) to ship compiled Bun binaries. A Node factory would use `node-pty` instead. The `IPty` interface is the same shape.

**vibe-kanban: learn from (protocol, not UI).** Its Claude executor runs `claude` with `--output-format=stream-json --input-format=stream-json --include-partial-messages --replay-user-messages --permission-prompt-tool=stdio`, and resumes with `--resume <id>` / `--resume-session-at` ([claude.rs](https://github.com/BloopAI/vibe-kanban/blob/main/crates/executors/src/executors/claude.rs)). This is the headless control protocol that also underlies the Agent SDK. It is the right channel for AFK runs: structured events, permission prompts, usage numbers. It also exposes an MCP task server ([crates/mcp](https://github.com/BloopAI/vibe-kanban/tree/main/crates/mcp)) that lets agents create and read tasks, which is a precedent for the factory MCP tool. Do not depend on it: it is Rust, a web UI, and has no company behind it.

**Claude Agent SDK: candidate executor, decided elsewhere.** It provides hooks, a `canUseTool` permission callback, subagents, in-process MCP servers (a natural home for the "spawn child task" tool) and session resume/fork. It is the obvious engine for AFK runs. One constraint matters for the billing ticket: the SDK docs state that "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK." Whether a single operator's own tool on their own Pro/Max login falls under that needs to be settled in the billing/executor tickets. The interactive `claude` CLI in a PTY has no such ambiguity. The demos repo (hello-world, research-agent, email-agent, simple-chatapp and others) shows usage patterns only; there is nothing orchestration-specific to reuse.

**agent-deck: learn from (metrics UX).** It has the best existing token/cost tracking: a TUI `$` dashboard (today/week/month, top sessions, per-model breakdown), history backfilled from Claude transcript files, a pricing override table, budgets, and a context-window bar ([README](https://github.com/asheshgoplani/agent-deck#cost-tracking-dashboard)). Groups, archive (stop tmux but keep worktree and lineage) and parent linkage map onto the factory's groups and task trees. It cannot be reused on native Windows because of tmux. Its README also warns that plan limits assume ordinary individual use and recommends an API key or Team/Enterprise for heavy unattended orchestration. That point is relevant to the billing ticket.

**Claude Squad: learn from only.** It has a simple worktree-per-session UX with preview/diff tabs and checkout/pause/resume. It is AGPL and depends on tmux, so it is neither reusable nor portable to native Windows.

**claude-flow / Ruflo: different paradigm.** It is a swarm-and-memory layer installed *into* Claude Code: it writes `.claude/`, `.claude-flow/` and `CLAUDE.md`, and registers an MCP server with hundreds of tools. It neither manages parallel worktree sessions nor provides an operator TUI in the factory's sense. At most it could be skimmed for its routing ideas. Its invasiveness conflicts with reproducible, pinned skill provisioning.

**Crystal, Conductor: ignore.** Crystal is deprecated in favour of an Electron workspace (Nimbalyst). Conductor is a Mac-only commercial app.

**Recommendation for the TUI ticket(s):** prototype on **Ink 8** for the dashboard: task tree, groups, attention queue and metrics. Use **ccmanager-style full-screen attach** for live HITL conversations, so there is no need to draw a terminal inside an Ink pane in v1. Keep **OpenTUI** as the alternative if "several live session panes side by side" becomes a hard requirement. Its embedded-terminal widget solves that directly, at the cost of a pre-1.0 dependency and either Bun or Node 26 with experimental FFI. A small spike rendering 4–8 live `@xterm/headless` buffers inside Ink boxes would settle the performance question for Ink. No primary source benchmarks it.

## 3. Embedding an interactive terminal session (Windows first, Mac later)

### Building blocks

- **`node-pty` 1.1.0** (2025-12-22; beta 1.2.0-beta.15, 2026-08-03) ([repo](https://github.com/microsoft/node-pty), [typings](https://github.com/microsoft/node-pty/blob/main/typings/node-pty.d.ts)). Uses ConPTY on Windows 10 1809+ (winpty support removed). The npm package carries **prebuilt binaries for `win32-x64`, `win32-arm64` and darwin**, so normally no compiler toolchain is needed. The install script falls back to `node-gyp rebuild`, which needs VS Build Tools and Spectre-mitigated libs. Linux has no prebuilds (irrelevant now). It also bundles `conpty/conpty.dll` + `OpenConsole.exe`, selected with the **experimental** option `useConptyDll: true` to bypass the OS's inbox ConPTY. `useConpty` is deprecated and ignored. `conptyInheritCursor` maps to `PSEUDOCONSOLE_INHERIT_CURSOR`. "node-pty is not thread safe," so keep all PTYs on the main thread of whichever process owns them. Optional XON/XOFF flow control (`handleFlowControl`). Licence: MIT-style (GitHub reports NOASSERTION; **unverified** exact text).
- **`@xterm/headless` 6.0.0** (2025-12-22; 6.1 betas ongoing) ([README](https://github.com/xtermjs/xterm.js/tree/master/headless), [typings](https://github.com/xtermjs/xterm.js/blob/master/typings/xterm-headless.d.ts), [6.0.0 notes](https://github.com/xtermjs/xterm.js/releases/tag/6.0.0)). A full xterm.js parser and buffer in Node, with no DOM. The README still labels it "experimental", although ccmanager ships on it (VS Code's terminal persistence reportedly does too: **unverified**). 6.0 added **synchronized output (DEC 2026)**, removed the deprecated `windowsMode`, fixed the headless `exports` path, and moved its demo to node-pty's `conpty.dll`. `@xterm/addon-serialize` produces a VT snapshot to repaint a session on attach. MIT.
- **Alternative PTY:** `Bun.Terminal` (ConPTY on Windows) if the factory ever runs on Bun ([Bun docs](https://bun.com/docs/runtime/child-process)).

### What breaks on Windows (and how to handle it)

| Issue | Source | Mitigation |
|---|---|---|
| **Resize/reflow.** With the inbox ConPTY below build 21376, xterm.js disables reflow and assumes lines are wrapped when the last char is non-whitespace. ConPTY also adds empty rows rather than pulling scrollback down when rows grow | `windowsPty` docs in xterm typings | Always set `windowsPty: { backend: 'conpty', buildNumber }` on the headless terminal. The operator is on **build 19045**, so expect no reflow unless the bundled `conpty.dll` is used. Whether a newer `buildNumber` may be declared when `useConptyDll` is on is **unverified**: test it |
| **Output is re-encoded.** ConPTY is itself a terminal emulator: it re-renders the child's screen and emits its own VT, so sequences differ from what the child wrote; termios flags read as 0 | [Bun child-process docs](https://bun.com/docs/runtime/child-process) (Windows differences) | Treat the PTY stream as a screen, not a log. Use Claude Code hooks or stream-JSON transcripts for structured events, never parsed PTY bytes |
| **Mouse tracking does not work on Windows 10 / Server 2019** | same Bun docs | Matters for the operator (Win10). Rely on the keyboard inside embedded sessions; test whether `useConptyDll` fixes it **(unverified)** |
| **Cursor-position request hang.** With `PSEUDOCONSOLE_INHERIT_CURSOR`, the host must answer the cursor query asynchronously or "may cause the calling application to hang" | [CreatePseudoConsole](https://learn.microsoft.com/en-us/windows/console/createpseudoconsole) | Leave `conptyInheritCursor` off, or pipe `@xterm/headless` `onData` replies (DSR/DA responses) back into the PTY |
| **Synchronous I/O only** on the ConPTY pipes | same Microsoft doc | node-pty handles this internally; do not wrap PTYs in worker threads |
| **Host terminal capabilities.** The outer terminal must handle truecolor, alt screen and synchronized output | [Windows Terminal releases](https://github.com/microsoft/terminal/releases) | Windows Terminal supports DEC 2026 synchronized output since Preview 1.24.2372.0 (2025-08-26), backported to stable 1.23.20211.0 (2026-01-24). Current stable is v1.25.2733.0 (2026-10-02). Target Windows Terminal, not legacy conhost |
| **Key-protocol leakage** between the Ink host and the child (kitty keyboard, modifyOtherKeys, focus reporting, bracketed paste) | ccmanager [Session.tsx](https://github.com/kbwo/ccmanager/blob/main/src/components/Session.tsx) | Reset these modes when entering and leaving an attached session, as ccmanager does |
| **Colours.** ConPTY passes 24-bit colour, but children decide by env | OpenTUI embedded-terminal docs recommend setting `TERM`/`COLORTERM` | Spawn children with `TERM=xterm-256color`, `COLORTERM=truecolor` |
| **Claude Code on native Windows** uses Git Bash for its Bash tool, or PowerShell if Git for Windows is absent; sandboxing is not supported natively | [Claude Code setup](https://code.claude.com/docs/en/setup) | Not a PTY issue, but affects reproducibility of AFK runs; see the isolation/Docker tickets |

**Mac later:** node-pty uses `forkpty` with prebuilds for darwin-x64/arm64, and none of the ConPTY rows apply. The same code path works. Only `windowsPty` is dropped.

### Fit with "should runs outlive the TUI?" (#10)

The snapshot model generalises to a daemon. The daemon owns the `node-pty` processes and one `@xterm/headless` per run, and the TUI client asks for a serialized snapshot followed by the live byte stream. Closing the TUI then leaves runs alive. ccmanager does the in-process version of this today.
